## Colour UI: transparency slider, slider double-clicks, swap/reset placement

User request (verbatim):
> at the color picker below the lightness slider there should also be a
> transparency slider
> also double click left on the lightness slighter sets the color to dark,
> double click right mouse sets it to bright
> same double click on the transparency slider sets it to alpha 100 and right
> mouse button double click to alpha 0
> also the switch colors button should be between foreground and background
> color and the reset icon should similar to paint.net have a preview of the two
> colors, so a black and white rectangle

### Where things live

- The picker the user means is **`components/shell/ToolbarColorPicker.svelte`**
  (bottom of the left tool column) — NOT `ColorPickerPanel.svelte`, which is the
  full "Colour" mode and already had hue + alpha strips. The toolbar one had a
  hue/sat area + a single brightness slider and always committed `a: 255`.
- The swap/reset buttons live in **`components/shell/ColorBar.svelte`**, styled
  by `.color-stack` / `.cs-fg` / `.cs-bg` in **`src/routes/layout.css`**.

### What changed

`ToolbarColorPicker.svelte`
- New `alpha` state (0..255) synced from `$foregroundColor.a` **outside** the
  existing rgb guard in the sync effect — alpha can change on its own (full
  picker panel, reset, eyedropper) while r/g/b stay put, and the guard would have
  skipped it. The effect never *reads* `alpha`, so writing it cannot loop.
- `commit()` and `applySelected()` now carry alpha. The background slot keeps its
  own alpha (`backgroundColor.update`) instead of being clobbered by the fg
  slider.
- New transparency range input below the brightness one, 0..100 in **slider
  units** where 0 = opaque and 100 = invisible; alpha is derived from it
  (`alpha = round((1 - t/100) * 255)`). Thumb shows the colour at its real alpha.
- The alpha track is a colour→transparent gradient over a **mid-grey**
  checkerboard (`#6a6a6a`/`#454545`), not the swatches' near-black one: an opaque
  BLACK left end vanished against `#383838`.
- Shared `isDoubleClick(e, zone)` helper replacing the inline `lastClick` check.
  `dblclick` only ever fires for the primary button, so the right-button half of
  every gesture is tracked by hand; `zone` stops a click on one control pairing
  with a click on another.
- `onBrightnessUp`: dbl-left → `l = 0` (dark), dbl-right → `l = 100` (bright).
- `onTransparencyUp`: dbl-left → `alpha = 255`, dbl-right → `alpha = 0`. Because
  the slider reads *transparency*, its ends are the alpha extremes the other way
  round — which is what makes left/right mean the same visual direction on both
  sliders.

`ColorBar.svelte` + `layout.css`
- Stack widened 40 → 56px and the swap button moved **inside** it at
  `left: 25px` (fg 0–25, swap 25–41, bg 41–56) — literally between the swatches.
  It is deliberately low-key (transparent, dim `#9a9a9a`, hover brightens).
- The reset button is no longer the `↺` glyph: it is a 20×18 chip showing a
  12px **black square over a white square** (the default colour pair), Paint.NET
  style — the icon now previews what it resets to.

### Gotchas worth remembering

- **A range input never reports a right-button value change**, so a right-button
  double click has to be detected from `pointerup` (button === 2) and applied by
  hand — and `contextmenu` must be prevented or the menu pops up over it.
- **Tailwind v4 emits `oklch()`** for utility colours, so never match
  `bg-blue-500` by computed `rgb()`; match the class instead.

## Effects: reuse the Mandelbrot XY pad + rotation dial

User request (verbatim):
> in the mandelbrot effect there is some xy slider and some rotation slider.
> this should be used for the zoom blur (the xy controller) and for the
> rotatory blur and radial blur, twist

### Where things live

- The registry already had both control kinds: `EffectParam.kind` is
  `'slider' | 'color' | 'checkbox' | 'xy' | 'angle'`. An `xy` param writes
  `settings[keyX]` / `settings[keyY]`; an `angle` param binds `settings[key]`.
- Widgets: `components/common/XYPicker.svelte` + `XyParam.svelte` (pad),
  and the `angle` dial. Mandelbrot's dialog was the reference implementation.
- `XYPicker`'s pad default maps left→minX, right→maxX, **top→maxY** (a maths
  graph). New `yDown` prop flips it so top→minY — correct for a POSITION in
  image space, where y grows downward like the canvas.

### What changed

- `types.ts`: `EffectParam.yDown?: boolean`.
- `XyParam.svelte`: `yDown={param.yDown ?? false}`.
- `registry.ts`: `defaults` now seeds **both** halves of an `xy` param —
  `` `${p.key}X` `` and `` `${p.key}Y` `` (the latter from `p.defaultY ?? p.default`).
  Without this the shader uniform got `undefined` → NaN and the preview went blank.
- All four effects got `yDown: true` on their `center` pad:
  - `zoomBlur.ts` — centerX/centerY sliders → one `center` pad. No angle param,
    so correctly no dial.
  - `rotaryBlur.ts` — center → pad; angle 0..180 slider → `kind: 'angle'`,
    −180..180. `isNoop` `angle <= 0` → `angle === 0` (negatives are now
    reachable, so `<= 0` would have no-opped them).
  - `radialBlur.ts` — center → pad; angle 0..360 slider → `kind: 'angle'` 0..360
    (a full turn, so the dial wraps). Quality slider kept.
  - `twist.ts` — center → pad; angle −360..360 slider → `kind: 'angle'` −180..180.

### Range trade-offs (the important bit)

- **Rotary Blur is not a behaviour change.** Its shader averages over the arc
  `[-a/2, +a/2]` — the same sample set for `+a` and `-a` — so 0..180 and
  −180..180 describe the same effect.
- **Twist is a real reduction.** It used to reach 360; the dial can only express
  one turn, so it is capped at 180. Since twist scales the angle by radius
  (`theta = angle * f(r)`), 360 is *not* equivalent to 0, so the maximum twist is
  now half what it was. Flagged to the user; restoring it needs a second control
  (a slider beside the dial).
- **Radial Blur** 0..360 is exactly one turn, so the dial loses nothing.
- The `AnglePicker` dial **clamps** unless its range is ≥ 359°, in which case it
  wraps. That is why Rotary/Twist were given symmetric full-circle ranges rather
  than their original asymmetric ones.

### Verified headless (1400×900)

`fx-controls.mjs` — **13/13 PASS**: all four dialogs open with a pad; Rotary /
Radial / Twist also show a dial (Zoom Blur has none, correctly); no "Center X/Y"
slider survives anywhere; the pad reaches its range with Y pointing DOWN — pad is
120×120, dragging to each edge midpoint gives left `[3,50]`, right `[98,50]`,
top `[50,3]`, bottom `[50,98]`; Apply renders a real blur (109/250 scanline
samples changed); no NaN (white stays white).
`fx-shots.mjs` — `fx-zoom-blur.png`, `fx-rotary-blur.png`, `fx-radial-blur.png`,
`fx-twist.png`.
tsc clean, svelte-check **0 errors / 52 warnings** (baseline), zero console errors.

### Gotchas worth remembering

- **The XY pad is a rounded rect**: its literal corner pixels hit the wrapper
  (`.xyp-body`), not the pad (`.xyp-pad`). Probe the **edge midpoints**, not the
  corners, or the drag never starts and the values look frozen at their default.
- **An `xy` param needs both defaults seeded** (`registry.ts`) or the preview
  renders NaN/blank — a blank preview after adding an `xy` param is this, not the
  shader.

## Menus: clicking a submenu header must never close it

User request (verbatim, German):
> was mich auch schon seit langem etwas stört, generell bei menüs aber mal am
> beispiel des effekts menu. ich klicke auf effects, dann hovere ich auf blurs,
> dann öffnet sich das untermenü, aber wenn ich dann nochmal auf blurs klicke
> schließt es sich wieder. das ist unintuitiv. selbst wenn ich 10 mal auf blurs
> klicke soll sich kein einziges mal das untermenü schließen

### Root cause

`components/shell/MenuBar.svelte`, the submenu header button. Hover already
opens the submenu via `onpointerenter` on `.sub-holder`, but the click handler
**toggled**:

```js
onclick={() => (openSub = openSub === subKey ? null : subKey)}
```

So the pointer was already hovering the header (submenu open), and the click
immediately closed it — the click appeared to undo the hover. The next click
re-opened it, giving an alternating open/closed flicker per click.

### Fix

The click may only ever OPEN. New `openSubmenu(key)` sets `openSub = key`
unconditionally; re-setting the same key is a no-op, so any number of clicks
leaves it open. It still switches to a different submenu, and it lets the
keyboard open one with Enter.

`MenuBar.svelte` is the **only** place with this pattern — `ContextMenu.svelte`
has a flat list with no submenus, so nothing else needed the same change. The
top-level menubar button (line ~80) keeps its toggle deliberately: clicking
"Effects" again closing the whole menu is standard and was not the complaint.

### Verified headless (1400×900)

`submenu-click.mjs` — **15/15 PASS**, including the reported flow verbatim:
hover "Blurs" → submenu opens → 10 real clicks on the header → `open open open
open open open open open open open` (never closes), 9 effect items still
listed. Also covered: moving into the submenu keeps it open; clicking an item
still opens the effect (dialog "Frosted Glass"); hovering another header
switches and leaves exactly one header marked open; hovering away closes the
submenu but not the menu; clicking the menubar button closes the menu.

**The probe was confirmed to catch the bug**: restoring the old toggle line
made it print `CLOSED open CLOSED open CLOSED open CLOSED open CLOSED open` and
FAIL. (Note the naive "still open after the 10th click" check *passes* under the
bug, because click 10 is a closed→open — the per-click assertion is what makes
the test real.)

tsc clean, svelte-check **0 errors / 52 warnings** (baseline), zero console errors.

## Motion Blur: angle slider -> rotation dial (with a real direction fix)

User request (verbatim):
> und angle picker bei motion blur

### What changed

`effects/blurs/motionBlur.ts`: `angle` was a plain slider (`0..360`) -> now
`kind: 'angle'`, same `0..360` range (a full turn, so the dial wraps).

**The range change alone would have been wrong.** The dial reads 0 = up,
clockwise (the `AnglePicker` convention), but the shader's own theta is measured
from the +x axis with

```
vec2 endOffset = vec2(-uDistance * cos(uAngle), uDistance * sin(uAngle)) * texel;
```

in UV space, where y points DOWN. So shader theta = 0 points **left** and theta
grows **counter-clockwise** on screen — dial 0 would have produced a HORIZONTAL
blur. Fixed by re-anchoring in `filter()`:

```ts
uAngle: { value: ((90 - settings.angle) * Math.PI) / 180, type: 'f32' }
```

Derivation: we want the streak to run along the dial direction
`(sin D, -cos D)`. With `centered = 0` the shader samples `v + t*e`, so the
smear of a dot at P lands on `[P, P - e]` — it extends along `-e`. Setting
`-e = (sin D, -cos D)` and `e = (-cos t, sin t)` gives `t = 90° - D`.
So 0 -> vertical, 90 -> horizontal.

Note this changes how the **default 25** renders (it used to mean shader theta
25 = left-ish). That is the point: the dial now points where the streak runs.

### Verified headless (1400x900)

`motion-angle.mjs` — **11/11 PASS**. A black dot on a white layer, blurred with
`Centered` OFF, measuring the centroid shift of the darkened pixels (which IS
the tail direction):

```
  D   dial  centered   centroid shift      dir(x,y)          dot  streak box
    0     0     false   (   0.0,  -56.5)   ( 0.00, -1.00)   1.00  40x119
   90    90     false   (  56.0,    0.0)   ( 1.00,  0.00)   1.00  118x40
  180   180     false   (   0.0,   56.0)   ( 0.00,  1.00)   1.00  40x118
  270   270     false   ( -56.5,    0.0)   (-1.00,  0.00)   1.00  119x40
```

i.e. the dial direction and the streak direction agree to dot product **1.00**
at all four cardinal angles, 0° is vertical and 90° is horizontal.

`fx-controls.mjs` — now **15/15 PASS** (Motion Blur added): it shows the dial
(25, 0..360), no pad, and no "Angle" slider is left anywhere.
tsc clean, svelte-check **0 errors / 52 warnings** (baseline), zero console errors.

### Gotchas worth remembering

- **A shader's angle convention rarely matches a UI dial's.** Always check the
  shader's vector maths (`-cos`/`+sin` against a y-down UV space) and re-anchor
  in `filter()` rather than assuming 0 = up.
- **Blurring a small dot makes it GREY, not black.** Averaging a 40px dot over a
  ~115px streak leaves the darkest pixel around 200/255, so a "pure black"
  threshold finds *nothing* and the probe reports an empty result. Threshold on
  "not near-white" instead.
- **The dark transparency checkerboard contains PURE BLACK** (`#000000` squares,
  base `#241f21`), so it is indistinguishable from black artwork. Measure inside
  a box known to lie wholly within the image.

## Dialogs: the X (close) button did nothing — pointer capture ate the click

User report (verbatim):
> the x button for the zoom blur and probably also other blurs does not work,
> for cancel the close works

### Root cause

`common/MovableDialog.svelte`: `.m-close` lives INSIDE `.m-title`, and
`.m-title`'s `onpointerdown={beginDrag}` called
`setPointerCapture(e.pointerId)` on itself. **Capturing the pointer retargets the
subsequent `click` to the capture element**, so a real click on the X was
delivered to `DIV.m-title` and the button's `onclick` never fired. Cancel sits in
`.m-footer`, outside the capture, which is exactly why it worked.

Proven, not guessed — the probe records the capture-phase click target:

```
real click on X   : closed=false  click targets=["DIV.m-title"]
programmatic .click() on X : closed=true     <-- the trap
real click on Cancel       : closed=true
```

### Fix

Bail out of the drag when the gesture starts on a control:

```ts
function beginDrag(e: PointerEvent) {
  if ((e.target as HTMLElement | null)?.closest('button, a, input, select, textarea')) return;
  ...
}
```

`EffectPanel.svelte` already had this exact guard ("interactive children (the
close button) keep their own behavior") — `MovableDialog` was the one place that
was missed. One change fixes every dialog: Curves, Effect, ImageSize,
LayerEffect, Levels, Paste, RasterizeConfirm, SelectionSize all use it.

### Why this hid for so long (important)

**Every earlier probe closed dialogs with `document.querySelector('.m-close').click()`.**
`HTMLElement.click()` dispatches a `click` with NO pointerdown/up, so it can
never reproduce a pointer-capture bug. The probes were green while the button was
dead for real users. Real mouse input is mandatory for click targets that share
an ancestor with a pointer handler.

### Verified headless (1400×900)

`dialog-close-x.mjs` — **11/11 PASS**: a real `page.mouse.click` on the X closes
Zoom Blur and the click target is now `BUTTON.m-close`; Motion Blur, Rotary
Blur, Radial Blur, Twist, Image ▸ Resize… and Adjustments ▸ Levels… all close the
same way; programmatic `.click()` and real-click-on-Cancel still work as
controls; and the title bar still drags (delta 120,60 — the guard did not break
moving the dialog).
tsc clean, svelte-check **0 errors / 52 warnings** (baseline), zero console errors.

## Effects round 2: Emboss, Julia, Drop Shadow, Bulge, Warp (+ Relief, Bevel, Smudge)

User request (verbatim):
> for emboss, julia fraktal, drop shadow, buldge and wrap also use angle picker /
> xy controller wherever possible

### XY pads (the easy half)

An `xy` param writes `settings[keyX]` / `settings[keyY]`, so converting a
`centerX`/`centerY` or `offsetX`/`offsetY` pair needs **no change to `filter()`** —
only the param definition. Done for:

| Effect | Was | Now |
|---|---|---|
| Bulge, Warp, Smudge | `centerX`/`centerY` sliders | `center` xy pad, `yDown: true` |
| Julia Fractal | `centerX`/`centerY` (−100..100) | `center` xy pad, **no** `yDown` |
| Drop Shadow | `offsetX`/`offsetY` (±50 px) | `offset` xy pad, `yDown: true` |

`yDown` is set where the value is a POSITION in image space (Bulge/Warp/Smudge
focal point, the shadow's offset — the shader samples `uv - offset`, so +offset
moves the shadow down). Julia's centre is a point in the **complex plane**, not
the image, so it deliberately has **no** `yDown` — that matches Mandelbrot's
`offset` pad exactly (verified: both have their pad top at maxY).

### Angle dials (the half that needed real care)

Each shader has its OWN angle convention, and none of them was "0 = up,
clockwise" like the `AnglePicker` dial. Measured, not assumed:

| Effect | Shader | Mapping |
|---|---|---|
| Motion Blur | `e = (-cos t, sin t)` | `t = 90 - D` |
| Emboss | `d = (cos t, sin t)` = light-TRAVEL direction | `t = 90 + D` |
| Bevel | `(lx, ly) = (cos t, sin t)` = light-TRAVEL direction | `t = 90 + D` |
| Relief | `lightDir = (cos t, sin t, 0.6)` = direction TO the light | `t = D - 90` |

The sign flips between Emboss/Bevel and Relief because their shaders disagree on
whether the vector points at the light or away from it. **Deriving this is
error-prone — every one was confirmed on pixels** (see below).

### Defaults were re-picked to keep the default LOOK identical

Because the mapping changed, the number that produces the old rendering moved.
The old shader angles were emboss 45, relief 45, bevel 135, so:

- emboss `ANGLE` 45 → **315** (`90 + 315 = 405 = 45`)
- relief `ANGLE` 45 → **135** (`135 - 90 = 45`)
- bevel `ANGLE` 135 → **45** (`90 + 45 = 135`)

A fresh install therefore renders exactly as before; only the number the dial
shows changed, and it now points at the light. (Anyone with a *stored* custom
angle still sees their angle reinterpreted — unavoidable, since the meaning of
the number changed.)

### Gotchas worth remembering

- **A lighting/emboss response is centred ON the boundary**, not inside it: a
  sample band a few px inside the shape reads the flat output and shows no
  direction at all (my first attempt measured 128.0 on every edge).
- **Bevel works on ALPHA**, so it needs an alpha edge (an opaque ground makes it
  a no-op) and a source that can be brightened — on white the highlight clamps
  to nothing. Use a BLACK square on a TRANSPARENT ground: only the lit edge
  lights up.
- **`EffectDialog` persists last-used settings** (`effects.<id>` in
  localStorage, key `paint.svelte.settings.v1`), so a probe cannot observe the
  shipped default after touching the dialog. Delete that key first — otherwise
  the "default" you read is whatever the previous section left behind.
