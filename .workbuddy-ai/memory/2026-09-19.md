# 2026-09-19 — paint.svelte

## FilterSlider: centre marker is now a DOT, not a line

Requested: *"for the FilterSlider component, please visualize the center not
with the line as it is atm but with a dot in the middle"*.

`.fsl-tick-center` was a 2px full-height rule (`top: 3px; bottom: 3px`). It is
now a 5x5 round dot centred on the track both axes:

```css
.fsl-tick-center {
	position: absolute;
	left: 50%;
	top: 50%;
	width: 5px;
	height: 5px;
	transform: translate(-50%, -50%);
	border-radius: 50%;
	background: rgba(255, 255, 255, 0.5);
	box-shadow: 0 0 0 1px rgba(0, 0, 0, 0.25);
	pointer-events: none;
}
```

Kept the same colour/ring so it stays "deliberately subtle". Bonus: the old
line was **shape-identical to `.fsl-pos`** (the value-position line on gradient
tracks), so the two were easy to confuse; a dot can't be mistaken for it.

The prop is still named `centerTick` (renaming it would touch 4 call sites and
8 effect files for no behaviour change) — only its doc comment was updated.
It is used by: brightCont, exposure, highlightsShadows, hueSat, smudge, twist,
warp, glow.

Verified with `.workbuddy-ai/fsl-center-dot.mjs` — **6/6 PASS**, dot geometry
measured, not eyeballed: `size 5x5 radius 50%`, and
`dot(686,309) vs track(686,309)` — dead centre on both axes.

Note: at value 0 the thumb sits exactly ON the centre and hides the marker
(true of the old line too). The marker is read when the thumb is elsewhere —
captured as `fsl-center-dot-offset.png` (value 90, `covered by thumb = false`).

## The probe suite had gone stale — the app changed underneath it

The user said "a lot has changed". Two harness assumptions were dead, and both
failed **silently**, producing plausible-looking numbers:

1. **`FilterSlider` has no `input[type=range]` any more.** It is a custom
   track (`role="slider"`, `.fsl-track` / `.fsl-well` / `.fsl-thumb`). Every
   probe that drove `.m-dialog .fsl-range` matched **nothing**, so `setSlider`
   was a no-op — while the dialog happily kept its *persisted* values and the
   canvas still changed, so the run looked successful.
   Verified by dumping the dialog: `.fsl-range=0  .fsl-track=2  .fsl-input=2`.
   Fix: drive the always-editable `.fsl-input` (its `input` handler parses and
   calls `setValue`) and read back `aria-valuenow` from `.fsl-track`.
2. **The Effects menu is no longer a `.menu-panel`.** `MenuBar.svelte` now
   branches: `{#if menu.label === 'Effects'}<EffectBrowserMenu …/>{:else}<div
   class="menu-panel">…`. So `Effects ▸ Render ▸ Clouds` matched nothing and
   the base scene was never built. `Adjustments` still uses `.menu-panel`, so
   only the Effects-based scene builders broke. Rebuild scenes with tools (the
   Paint Bucket) or via Adjustments instead.

Both are the same failure mode as the earlier `.fsl-range` discovery: **a
selector that matches nothing is indistinguishable from a passing test.** Added
a guard to the probes — read the control count first and hard-fail if the
driver finds 0, instead of reporting a vacuous pass.

## Re-verified the Highlights/Shadows fix against the current app

The earlier Highlights numbers were produced with the broken driver, so they
were re-run properly. Base built without the Effects menu: Paint Bucket (fills
the foreground, black) → `Adjustments ▸ Brightness / Contrast` at +100 twice →
uniform base at mean 178.4.

```
PASS  Highlights +90  178.4 -> 199.3   (up,   +20.9)
PASS  Highlights -90  178.4 -> 102.5   (down, -75.9)
PASS  Shadows +90     178.4 -> 178.4   [mask 0.027 — near no-op expected]
PASS  Shadows -90     178.4 -> 176.6   (down,  -1.7)
PASS  Highlights +90 brighter than -90
5/5 PASS
```

The fix holds: **+90 brightens, −90 darkens**, and +90 out-brightens −90 (the
old bug had −90 brighter). Probe: `fx-hlsh-verify2.mjs`.

The assertion is now **mask-aware** and that matters: both sliders are masked by
the base's own luminance (`pow(luma,3)` / `pow(1-luma,3)`), so on a BRIGHT base
`Shadows +90` is legitimately sub-LSB (mask 0.027) — requiring it to move would
be a wrong expectation, not a bug. On a BLACK base the same case moves the mean
by ~200. A uniform base also moves the mean without tripping a >24/px diff
threshold, so the diff count is reported for context, not asserted.

## Fixed a new type error in vite.config.ts

`npm run check` had gone from 0 errors to **1 error** — not from this work:
`vite.config.ts(16,56): Type 'null' is not assignable to type 'string | undefined'`.
`adapter-static` 3.x declares `fallback?: string`, so `fallback: null` is
invalid; omitting the key means the same thing (no SPA fallback). Removed it.

Baseline is now **0 errors / 55 warnings** (was 52 — the recent refactor added
3 warnings; worth a look, they may be real).

## Tool-options bar restyled to the `selection-toolbar.html` design

Requested: *"now make the toolbar more similar to this designed from claude:
selection-toolbar.html"*.

The reference is a **selection toolbar**: a raised chrome plate, a recessed
segmented control whose active pill is BLUE, a split dropdown (cycle + ▾), a
faint hint, and one blue primary action. The app's `.options-strip` was a flat
`--bg-elev` fill with a GREY active pill and ghost buttons.

Key discovery: `FilterSlider.css` already uses `linear-gradient(#3a3e45,
#272a2f)` — **the reference's exact button gradient** — so the codebase had
already been drifting toward this palette. That made the palette choice
obvious rather than invented.

### What changed

New `:root` tokens in `layout.css`: `--chrome-hi/--chrome-lo` (`#2b2e34`,
`#1a1c20`), `--chrome-bar1/--chrome-bar2` (`#34383f`, `#22252a`), `--well`
(`#0d0f11`), `--text-faint` (`#5d626c`), `--accent-glow`, `--accent-ring`
(`#6fd4ff`).

- `.options-strip` — gradient plate + a grain texture, lit top edge and a
  shadow under it. The grain is `background-blend-mode: overlay` blended **into**
  the plate, not a `::after` overlay: an overlay pseudo-element paints above
  in-flow content, so it would sit on top of the labels. Blending it into the
  background keeps every glyph crisp.
- `.seg-btn.on` — the signature change: grey `#3d434c→#2c3138` becomes the blue
  3-stop `#3f82f2 → #2c6fe0 55% → #2158b8` with a `0 0 10px rgba(60,130,255,.28)`
  glow. Shared class, so it also restyled the Resize Image dialog and the
  colour-picker panel — verified they still read correctly.
- `.tb-btn` / `.tb-btn.primary` — NEW toolbar action buttons. Deliberately NOT
  `.mini-btn`: that class is also the Layers panel's `＋ ⇩ ⧉ ↑ ↓` icon row, and
  turning those into raised gradient plates would be wrong. `.mini-btn` keeps
  its ghost styling; only the strip moved to `.tb-btn`.
- `.tb-divider` — 24px vertical hairline between control groups (8 of them).
- `.hint` — `--text-faint`, a step dimmer than `.aa-label`; applied to
  "Shift: square" and the other secondary hints, which were previously the same
  weight as real labels.
- `.fsl-num` — the number field now sits in the same `--well` groove as `.seg`
  instead of a lighter `--bg` box floating on the plate.
- `IconSplitButton.css` — raised plate, hairline between the icon and ▾ halves,
  arrow rotates when open, gradient menu panel with an accent hover.

### `ml-auto` was the wrong call — the tab tray owns the top-right

The design pushes its primary action flush right (`ml-auto`). I did that first,
then measured: `.tab-tray-overlay` is `position:absolute; left:75%; height:64px;
z-index:40` — it spans the menubar AND the options strip. The Crop button landed
at x 1262–1393, inside the tray box, and `elementFromPoint` at its centre
returned `DIV.fltab-tray`, so the click never reached the button. Reverted to
in-flow placement and kept the design's *look* rather than its right-alignment.

### Found and fixed a real bug while measuring: the tray swallowed clicks

The tray is a transparent box that happens to hold tabs, and it had
`pointer-events: auto`, so its **empty** area ate clicks aimed at the menubar
and options strip underneath (the whole top-right 25% of the window). Fixed with
`pointer-events: none` on `.tab-tray-overlay` and `pointer-events: auto` on
`.fltab`. Verified: empty tray points now resolve to `DIV.menubar-strip` /
`DIV.flex` instead of the tray, and a real mouse click still switches tabs
(active 1 → 0). Trade-off: the tray's own horizontal scrollbar is no longer
draggable (wheel over a tab still scrolls it).
