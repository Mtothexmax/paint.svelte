# 2026-09-11 — Paste UX

## Reported (todo2.txt)
*"when pasting an image it is somehow sometimes weirdly placed so that the top left of the pasted image is in the center of the canvas. it should be placed at the top left of the canvas but even better, if pasting show a dialog like paint.net that asks expand canvas, keep canvas size or reset, but only if the dimensions are bigger than the image. also make that dialog so cool like in paint.net where the options are only 3 big buttons and above it the text with already a preview in small of the image to paste"*

## What I shipped
1. **Top-left paste (default).** Both paste paths (`pasteAsNewLayer` for the internal clipboard, `pasteBitmapAsLayer` for Ctrl+V with an image on the OS clipboard) now share `placePastedImage(srcId, w, h, ownsSource)`, which blits at `(0,0)` instead of centred.
2. **Paint.NET-style oversized dialog.** Shown ONLY when the pasted image is bigger than the canvas. Three choices: **Expand Canvas**, **Keep Canvas Size**, **Cancel** (the user's third option — clarified to be the no-op / cancel choice).
3. **Dialog design.** `PasteDialog.svelte` mounted via DialogHost. 360 px wide. Top: 104 px checkerboard preview box + the lead text "The image you are pasting (W × H) is larger than the canvas (W × H). What would you like to do?" Below: three big stacked buttons with title + hint. Primary button ("Expand Canvas") uses the accent colour.
4. **Preview generation.** New `surfaceToPngThumbnailUrl(renderer, surfaceId, w, h, maxSize = 180)` in `render/export.ts` — renders the source surface scaled to ≤180 px into a temporary RenderTexture, extracts to a PNG data URL. Cheap even for a 6000 px screenshot.
5. **Canvas resize for "Expand".** Reuses `resizeCanvas(renderer, max(w, imgW), max(h, imgH), -1, -1)` from `render/resize.ts` — top-left anchor, undoable 'Canvas Size' history entry. Then paste at (0,0) on the now-bigger canvas.
6. **Dialog footer.** `MovableDialog.svelte` no longer renders the empty footer strip when no `actions` snippet is provided. The paste dialog puts its own buttons in the body, so the footer would otherwise be a 37 px empty bar. All five existing dialogs already pass `actions`, so no behavioural change elsewhere.
7. **Safety.** A module-level `pendingOversize` cancels any earlier (unanswered) oversized paste when a new one opens, releasing its owned source surface. The paste blits are guarded by `surfaces.has(srcId)` so a copy made while the dialog was open cannot crash.
8. **Bug fix.** After `resizeCanvas` the doc selection is cleared (its `commitResize` already does this on redo). Acceptable for the paste flow.

## Verification (headless Chrome on the dev server)

  - Expand   → size 1600 × 900, +1 layer
- 300 × 200 paste into any larger canvas → no dialog (fits), paste at top-left.

## Status bar: the three read-outs got icons

Requested: *"when drawing a rectangle i see 3 dimensions in the bottom bar, i
want icons ... to tell me what is the dimension of the image, what is the mouse
position (a mouse icon) and what is the rectangle i am drawing."*

The strip showed three bare, indistinguishable numbers (`800 × 600`,
`142 × 99`, `(377, 337)`). Each now leads with a Material Symbols (rounded)
glyph:

| Icon | Meaning |
|---|---|
| `photo_size_select_large` | image/document size (still a button → Image Size dialog) |
| `crop_free` | the rectangle being drawn (live drag or committed selection) |
| `mouse` | pointer position |

All three carry a `title` tooltip; the cursor read-out dropped its parens.

**Colour decision (user-corrected):** I first tinted them blue / amber / green
to tell them apart. The user pushed back — *"i want the icons to be just light
gray, colors are nice but for this something less prominent like all just one
color is better"*. All three are now one muted grey, `#9a9a9a`, i.e. **dimmer
than the `#bdbdbd` values they label** (captions, not decoration). The button's
hover state brightens its glyph to `#cfcfcf` so it isn't stranded. Lesson for
future UI polish in this app: the user prefers restrained, monochrome chrome in
the status bar over multi-colour coding.

**Gotcha worth remembering:** the Material Symbols SVGs ship with **no `fill`**,
so they render solid black — invisible on the dark status bar. The codebase's
established fix (see `MenuBar`'s `.menu-svg`) is to import them `?raw` and inline
with `{@html}`, then colour the inner `svg` via `fill: currentColor` plus a
per-class `color`. Prefer that over CSS `mask-image` here: Svelte's scoped
`<style>` cannot reach `{@html}` children reliably, so these rules go in
`src/routes/layout.css` alongside `.notice` / `.status-dim`.

New CSS: `.sb-read`, `.sb-ic`, `.sb-image` / `.sb-marquee` / `.sb-mouse`;
`.status-dim` gained `gap: 5px`.

**Also fixed:** the pointer read-out kept the last pixel forever after the
pointer left the canvas. `onLeave` now clears `cursorX/Y` — but only when no
drag is in flight, since pointer capture keeps feeding moves after the pointer
leaves the host.

Verified headless: mid-drag / committed → 3 icons; pointer left → mouse read-out
gone; back → returns; Ctrl+D → marquee read-out gone. Image Size button still
opens its dialog. Narrow windows 1400→760 px: strip stays 25 px, no h-scroll,
zoom bar fully visible. Start screen: 0 read-outs. tsc clean, svelte-check
0 errors / 56 warnings, zero console errors.

Files: `src/lib/components/shell/StatusBar.svelte`, `src/routes/layout.css`,
`src/lib/components/canvas/EditorCanvas.svelte` (`onLeave`). Probes:
`.workbuddy-ai/statusbar-{probe,verify,narrow,nodoc,context}.mjs`.

## Resize Image: lock toggle between the dimensions

Requested: *"the resize image dialog must have a toggle button with a lock
between the dimensions instead of a checkbox with the label constrain
proportions, the label may stay as an alt text."*

The "Constrain proportions" checkbox is gone. A compact toggle now sits
**between** the Width and Height fields — the relationship it controls is
physically where it applies. Material Symbols rounded `lock` / `lock_open`,
16 px, `?raw` + `{@html}`; accent-tinted when locked, dim grey when free. The
words survive as `aria-label="Constrain proportions"` plus a stateful `title`.

**Behaviour change:** switching the lock ON now re-syncs the two values
immediately (the field edited last wins, same rule as typing). The old checkbox
did nothing until you touched a field, so you could "constrain", hit OK and still
get a distorted image — the one thing the lock promises not to do.

**Layout:** the row is `grid-template-columns: 1fr 32px 1fr`; the Scale row
reuses the same class so its single field lines up with Width exactly. The middle
column is a **fixed 32 px, not `auto`** — with `auto` the Scale row's empty middle
column collapses and its field drifts ~54 px wider.

**Reusable gotcha (hit twice now):** a scoped `<style>` rule that targets markup
injected via `{@html}` never matches — Svelte does not add its scoping class to
raw-injected nodes, and svelte-check reports it as *"Unused CSS selector"*. Fix
with `:global()`: `.lock-ic :global(svg) { fill: currentColor }`. The other two
occurrences (`MenuBar`'s `.menu-svg svg`, the status bar's `.sb-ic svg`) live in
the global `layout.css` for the same reason.

Verified headless (800×600 doc): 0 checkboxes in the dialog; lock `aria-label` +
`aria-pressed` correct; glyph `rgb(59,130,246)` on / `rgb(154,154,154)` off;
bottom edges flush (lock/width/height all 453); all three fields 187 px wide with
the same left edge. Locked 400 → height 300; unlocked height 500 → width stays
400; re-lock → width snaps to 667. Canvas Size mode: 9 anchors intact. tsc clean,
svelte-check 0 errors / 56 warnings, zero console errors.

Files: `src/lib/components/dialogs/ImageSizeDialog.svelte`. Probe:
`.workbuddy-ai/resize-lock.mjs` (+ `resize-lock-on/off.png`, `resize-canvas-mode.png`).

## Rotate gizmo: rings fixed + visible before the first click

Requested: *"for the rotation tool like in blender the circles for each axis must
not move while rotating but stay constant. also they must appear as soon as one
activates the rotate mode and not only when one clicks once."*

Two independent causes, both fixed:

**1. The rings spun with the content.** `MoveEngine.rotateRings` passed the live
`rot3` into `ringPolyline(axis, radius, this.rot3, center)`, so the gizmo rotated
with the thing it was rotating. `gizmoRadius()` was also derived from
`currentQuad()` — the *projected* quad — so the rings resized as the content
tipped through X/Y and the drag sensitivity (arc length ÷ radius) drifted with
them.

Fix: give the rings their own rotation-free frame.
- new `rotateRingsFor(center, radius)` in `render/move/gizmo3d.ts` — always
  `IDENTITY3`, only the fixed `GIZMO_TILT` applies. Blender's gizmo does not spin
  with the object; `rot3` rotates the **content only**.
- new `gizmoRadiusFor(bounds, scaleX, scaleY)` — from the **unrotated** selection
  box, so the radius is constant for the whole gesture.
- `beginRing()` hit-tests the exact same `rotateRingsFor(...)` output the overlay
  draws, so a click always lands on what the user sees.

**2. The rings only appeared after the first click.** The engine is created
lazily and reports `rotateRings: []` until `begin()` has lifted the pixels, so
the overlay had nothing to draw. Added `activeRotateRings()` in `EditorCanvas`:
engine rings if present, else built from `handleBounds` — the same fallback
`distortQuadPoints()` already used for the distort corners. Both
`rotateRingPaths` and `ringHandleAt` go through it.

Verified headless (800×600 doc, 300×230 selection): rings present immediately on
picking Rotate with **no canvas click**; ring `d` and bboxes **byte-identical**
after a 90 px Z-ring drag and an 80 px X-ring drag (the foreshortening case that
used to move + resize them); transform log shows `engine.rotateRingTo: 32`,
`engine.transformTo: 0` — both drags hit the rings, content genuinely turned.
tsc clean, svelte-check 0 errors / 56 warnings, zero console errors.

**Probe gotcha (cost me a full wrong diagnosis):** ring `<path>` `d` values are
**SVG-local** coordinates. The overlay is `absolute inset-0` inside the canvas
host, so a probe must add `ownerSVGElement.getBoundingClientRect()` before feeding
them to `page.mouse.move()` — otherwise the drags land beside the rings and
silently degrade into translations, which looks exactly like "the rings moved".

Files: `src/lib/render/move/gizmo3d.ts`, `src/lib/render/MoveEngine.ts`,
`src/lib/components/canvas/EditorCanvas.svelte`. Probe:
`.workbuddy-ai/rotate-rings.mjs` (+ `rotate-rings-idle/after-z/after-x.png`).

## Status bar: selection read-out opens an exact-size popup

Requested: *"when clicking on the rectangle selection toolbar that shows the
dimensions in the bottom toolbar one must also have a popup that appears that
lets one enter exact dimensions."*

The selection read-out was a plain `<span>`; it is now a `.status-dim` button
(same treatment as the image-size read-out beside it) opening a **non-modal,
movable** popup (`MovableDialog`) — so the canvas and the ants stay visible and
interactive while typing, and the popup can be dragged aside.

New: `src/lib/components/dialogs/SelectionSizeDialog.svelte`, `'selectionSize'`
in `dialogService.ts`, mounted in `DialogHost.svelte`, both StatusBar branches
turned into buttons.

Behaviour decisions:
- Pre-fills from the **live** selection bounds (falls back to the whole document);
  width field focused on open; Enter applies; Esc/Cancel are no-ops.
- The selection keeps its **top-left** corner — the predictable anchor when only a
  size is typed — and is clamped so it can never stick out past the canvas. A
  clamped input is called out in amber, since the applied size then differs from
  what was typed.
- Shape preserved: rect stays rect, ellipse stays ellipse. A lasso/polygon has no
  W×H of its own, so re-sizing it yields a rectangle.

Verified headless (800×600): read-out is a `BUTTON`; click opens title
"Selection Size", `aria-modal=false`, pre-filled 213×163, width focused; typing
400×100 → Apply → read-out 400×100; reopen reads the live selection back; typing
99999 clamps to 607 (= 800 − 193) with the amber note; Cancel and Escape leave
the selection untouched. **Ellipse proven by pixels**: fill layer, ellipse-select,
force 200×200, Delete, then eyedropper the bounds' corner → still `#000000 A255`
(an ellipse does not cover its corner) while the centre is `A0`. tsc clean,
svelte-check 0 errors / 56 warnings, zero console errors.

**Svelte gotcha:** a leading space inside `{#if}` is **trimmed by the compiler**,
so `{x}{#if c} · suffix{/if}` renders as `(...)·suffix`. Use an entity (`&nbsp;·`)
or an expression — entities are never trimmed.

Files: `SelectionSizeDialog.svelte` (new), `dialogService.ts`, `DialogHost.svelte`,
`StatusBar.svelte`. Probe: `.workbuddy-ai/selection-size.mjs`
(+ `selection-size-popup.png`, `selection-size-clamped.png`).
