## 1. Layers panel header — buttons were 6.25px below the title

Root cause: `justify-between` + `align-items: center` centres the title's whole
**box**, and `.panel-title` carried `padding-bottom: 4px` + `border-bottom: 1px`
+ `margin-bottom: 6px`. So the *text ink* sat ~3.25px above the box centre and
the box ran ~3px below the icon row.

Fixed structurally, not with a `transform` nudge: `.panel-head` (a new opt-in
class on the row, used only by `LayersPanel.svelte`) moves the rule to a
pseudo-element and reduces the title's box to exactly its text, so
`align-items: center` aligns words with glyphs.

- Measured with a `Range` over the title's text node:
  **before `+6.25px` → after `+0.75px`, spread 0** across all six buttons.
  The residual 0.75px is font-metric (ascent/descent) and is exactly what
  `align-items: center` produces on the History panel's text.

## Hazard worth remembering

**Never issue two `Edit` calls against the SAME file in one message.** Each
`Edit` reads the file, replaces, and writes the *whole* file, so concurrent
calls race and one change is silently lost — the tool still reports
"Successfully edited" for both. This session lost four `layout.css` edits and two
probe edits that way (and one earlier `.ang-ring` edit). It is ~50/50 per pair.
Parallel edits across *different* files are fine. Audit with a grep after any
batched edit.

**D4 — the zoom slider.** It was a bare `<input type=range>` styled only with
`accent-color`, which Chrome paints as a fat rounded pill with a big flat blue
circle — the one control that didn't speak the app's design language. Restyled
to match `.fsl`: 6px sunken well, blue accent fill ending under the thumb,
knurled metal thumb. `appearance: none` + `::-webkit-slider-*` and
`::-moz-range-*` pseudo-elements (plus `-moz-range-progress` for the fill).

**The subtle part:** a native range thumb does *not* travel the full track — its
centre runs from `THUMB_W/2` to `TRACK_W − THUMB_W/2`. Painting the fill to the
raw value % left a visible sliver of empty track left of the thumb at 1%. So
`ZoomBar.svelte` computes a compensated `fillPct` and passes it as `--zb-fill`:
`((p * (TRACK_W − THUMB_W) + THUMB_W/2) / TRACK_W) * 100`, with
`TRACK_W = 110` / `THUMB_W = 9` mirroring the CSS. Verified: at 1% zoom
`--zb-fill: 4.09%` (= 4.5/110) and no blue is visible beside the thumb.

## 9. ⚠️ The git object store vanished mid-session — NOT caused by an edit

`.git/objects` (loose **and** packed — no `*.pack` anywhere) disappeared while I
worked, along with `refs/heads/main`, `refs/remotes/*` and `refs/stash`. Git now
reports *"not a git repository"*. `.git/HEAD`, `config`, `logs/HEAD` (full
reflog) and `FETCH_HEAD` survive; **the working tree is completely intact**.

Timeline: an early `git status --short` **succeeded** (so objects existed then);
the next mutating call, `git stash push -- src/`, aborted with
*"545ca8cb… is not a valid object"* — i.e. it detected the damage, created no
stash ref, and changed nothing. So the loss happened in between, in a window
where I ran only read-only file ops, `tsc`, `svelte-check` and the Chrome probes.

Most likely mechanism: a **concurrent git operation by another tool**. This
working copy is shared — `.git/refs/agents/…`, `.git/refs/codex`, `.git/cursor`
and `.git/opencode` (touched 09:28, mid-session) show Cursor/Codex/opencode all
have git integrations here. A racing/interrupted `git gc` (which moves loose
objects into a pack and then deletes them) is the shape of the damage. **Not
provable, so I did not claim a cause.**

**Recovery** (not performed — needs user consent): remote is
`https://github.com/Mtothexmax/paint.svelte.git`, reachable, `refs/heads/main`
= `cf9806c4dc0fc8798fc344159077541b7f0760e5`. The last *local* commit was
`0c961729` ("added ai model downloader") — one ahead of the remote, so that
commit's message is lost but its content is safe in the working tree. Path:
`git init` (recreates `objects/`, preserves `config`) → `git fetch origin` →
`git reset --mixed origin/main` (NOT `--hard` — the working tree is the only copy
of the last commit's content).

**Rule for this repo: read-only git only** (`status`, `diff`, `ls-remote`). Never
`stash`/`gc`/`reset` — other agents are live in the same `.git`.

## 10. ✅ Git fully recovered — same session, with the user's go-ahead

The repo is healthy again: **`git fsck` → 0 errors, 0 missing objects**, history
back to `cf9806c`, and `git write-tree` works (so committing is possible).
**The working tree was verified byte-identical throughout** (md5 manifest over
303 files in `src/ scripts/ docs/ static/`, hash `f80a99f3…` before and after).

Backups taken first (all still on disk):
`/tmp/paint-tree-backup.tgz` (whole tree, no node_modules/.git),
`/tmp/paint-index-broken.bak`, `/tmp/paint-logs-backup.tgz`.

**The fix, in order** — each step was blocked by something, so the order matters:

1. `mkdir -p .git/objects` — **this alone fixed "not a git repository"**. Git only
   needs the directory to exist; the objects then come from the remote. (Plain
   `mkdir`, not `git init` — so `config`, `HEAD` and the reflog were never touched.)
2. A **dangling ref blocked every fetch**: `refs/agents/ccaf68a2-…/checkpoints/
   turn/0` → `98d39ffe…` (an AI-tool checkpoint whose object was destroyed with
   everything else). Git refuses to fetch while any ref points at a missing
   object, and `git fetch <explicit refspec>` does *not* avoid it. Recorded its
   value to `/tmp/dangling-ref-record.txt`, then `git update-ref -d` it.
3. `git fetch origin` → pulled the full pack (2477 objects: 1381 blobs, 955
   trees, 125 commits).
4. **The fetch's ref write silently didn't land** — git reported
   `* [new branch] main -> origin/main` but `refs/remotes/origin/` did not exist
   and `update-ref` returned 0 having written nothing. Cause: **git could not
   create the missing parent directory**. Fix: `mkdir -p .git/refs/heads
   .git/refs/remotes/origin` first, then write the refs. (Plain `echo >` into a
   loose-ref path also works — git reads loose refs as plain files.) Once the
   dirs existed, ordinary `git update-ref` worked normally again.
5. **The index was unusable and had to be rebuilt.** `git fsck` showed 97
   "missing blob" errors — *all* referenced by `.git/index`, 30 of them real
   source files (`MovableDialog.svelte`, `FilterSlider.css`, `package.json`, …).
   `git write-tree` failed, so no commit was possible. `git reset` alone also
   failed (`unable to read 9d02bb08…`) because it reads the broken index on the
   way in. Fix: `rm .git/index` (backed up) **then** `git reset --mixed HEAD`.
   Worth noting: the missing blob was *not* reachable from HEAD — the pack was
   complete, only the index's staged blobs were gone.
6. **Reflog: one corrupt line.** `.git/logs/HEAD:127` and
   `.git/logs/refs/heads/main:125` both recorded the move *to* the destroyed
   commit `0c961729`, which made fsck report `invalid reflog entry`. Removed just
   those two lines with `grep -v` (backup: `/tmp/paint-logs-backup.tgz`) —
   deliberately **not** `git reflog expire`, which would have wiped 126 valid
   entries of the user's commit history along with it.

**Consequences the user should know:** `refs/heads/main` now points at
`cf9806c` (= `origin/main`), so the last local commit `0c961729` ("added ai model
downloader") is **gone as a commit** — its message is lost, but its content is
intact in the working tree and will reappear as ordinary modifications. The
index's staging state was necessarily discarded (it was unusable anyway) — the
67 modified + 116 untracked files are all still there, just unstaged. The
`refs/agents/...` checkpoint ref for that AI tool is gone (it was already
dangling). Nothing has been committed — that is the user's call.

**Lessons:** (a) "not a git repository" after object loss often just means
`.git/objects` is missing — recreating the empty dir is enough to get going.
(b) A single dangling ref will block every fetch, and git's error names it.
(c) Git's ref writes need their parent directory to already exist; a silent
no-op there looks exactly like a permissions problem.
(d) After object loss, the *index* is the thing that breaks committing, and it
must be deleted before `git reset` will run.

`.color-mode-head .color-mode-done` / `...:hover` — **two classes**, so they tie

(`:not()` contributes its argument's specificity). A single-class
`.color-mode-done:hover` `(0,2,0)` would LOSE, and the global
`filter: brightness(1.1)` would stack on top of the hover gradient. Hence the
explicit `filter: none` in the hover rule.
