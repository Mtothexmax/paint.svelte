## BUG FOUND + FIXED: two effects emitted non-premultiplied colour

Adding the colour row made an old bug reachable, so I measured it rather than
eyeballing it. With the shadow set to white at the default Opacity (128/255 =
0.502) the shadow band read **255** — an opaque white slab. A correctly
translucent shadow must read `0.502*255 + 0.498*backdrop(~16.7) ~= 136`.

Cause: `vec4(uColor, alpha)` emits **un-premultiplied** rgb, but Pixi blends
premultiplied (`src.rgb + dst.rgb*(1-src.a)`), so `rgb=1.0` at `alpha=0.5`
composites to `1.0 + dst*0.5` and clamps to white. Invisible while the colour
was black (0 stays 0) — glaring for anything lighter.

The codebase convention is premultiplied, and every other effect follows it:
`noisyColor * c.a, c.a` (addNoise), `c.rgb * ratio, newAlpha` (feather),
`screenRGB * src.a, src.a` (glow). Two effects broke it by emitting a
**constant** colour with a **variable** alpha:

- `object/shadow.ts` — `vec4(uColor * shadowA, shadowA)`
- `object/outline.ts` — `vec4(uColor * uIntensity, uIntensity)`

Both are exact no-ops at their defaults (shadow black, outline intensity 255),
which is why nobody noticed.

Measured after the fix: shadow white reads **136.1** (predicted ~136).
Outline: canvas mean drops 27.71 -> 21.91 when Intensity goes 255 -> 128;
before the fix both runs rendered opaque white and the drop would have been ~0.

Probes: `fx-shadow-color.mjs` (12/12), `fx-outline-premul.mjs` (4/4).

Reviewed and deliberately **left alone**: `photo/redEyeRemoval.ts`
(`mix(c.rgb, target, uStrength), c.a` — both inputs are already premultiplied,
so the mix stays premultiplied) and `stylize/outline.ts` (`ink` is a near-black
constant, 0.04, so the over-brightening is imperceptible).

## Gotchas worth remembering

- **A backtick inside a shader template literal breaks the build.** The GLSL
  sources are JS template strings, so a backtick in a comment there closes the
  string early and Vite 500s on the module (`[PARSE_ERROR] Expected a semicolon
  ...`). I hit this writing a comment that quoted `` `vec4(uColor, uIntensity)` ``
  in `object/outline.ts`, and the whole app failed to load. Guard:
  `.workbuddy-ai/scan-shader-backticks.mjs` — statically scans all effect modules
  (45 templates in 54 modules) for a tick inside a template. Keep comments in
  shaders backtick-free.
- **A Vite 500 on one effect module takes down the entire app.** The symptom is
  not an obvious error — the page renders an empty body and every probe times
  out waiting for `.menubar-btn`. `curl` the module directly to see the real
  Vite error page.
- **Wait for `.menubar-btn` (and for `.m-dialog`) instead of a fixed sleep.**
  After a source edit Vite is still rebuilding and a click that lands too early
  is silently swallowed, which looks like a random flake.
- **`HTMLElement.click()` bypasses pointer events** — it can never reproduce a
  pointer-capture bug. Use real `page.mouse.click` for anything in a title bar.

## New param kind: `kind: 'select'` (dropdown), for Motion Blur's Edge Behavior

The audit's control dump showed one last wart: Motion Blur's "Edge Behavior" was
a **slider** whose label had to spell its own options out —
`Edge Behavior (0:Clamp, 1:Wrap, 2:Mirror, 3:Transparent)` — because a range
track cannot show four named choices. It was the only such case in the project
(checked every effect file).

Added a real `select` kind:

- `types.ts` — `kind?: ... | 'select'` plus
  `options?: { value: number; label: string }[]`.
- `components/common/EffectSelect.svelte` (+ `.css`) — a labelled native
  `<select>` over `options` with an icon reset button, matching FilterSlider's
  look. `bind:value` on a `<select>` keeps the option's real type, so the
  numeric value round-trips into settings as a **number**, not a string.
- Wired into **both** `EffectDialog.svelte` and `LayerEffectDialog.svelte` —
  they each render params with the same branch chain, so a new kind must be
  added to both or the docked layer-effect dialog silently falls through to a
  slider.
- `blurs/motionBlur.ts` — `edgeBehavior` migrated; label is now plain
  "Edge Behavior".

Probe `fx-select.mjs` — 20/20 PASS. The widget checks are straightforward; the
render check took three attempts (see below).

### Gotchas worth remembering

- **A blur conserves the mean.** It is a local average, so the mean luminance of
  the whole canvas is *identical* before and after — my first attempt measured
  18.36 for the baseline and for every single mode. Any blur test must measure a
  LOCAL region or diff two frames, never a global mean.
- **An edge mode can only differ where the streak leaves the image, and the
  image's border must contain content.** My first setup put a block 4px inside
  the left edge; clamping then samples the *empty* border column, so Clamp
  matched Transparent exactly. Content has to touch the boundary.
- **A Rectangle Select drag started exactly on the canvas corner is rejected** by
  the app, so nothing gets drawn and the probe silently measures bare canvas
  (a strip read 30.00 — the app background — in every case). Inset the drag, or
  avoid geometry entirely: flooding the whole layer with the Paint Bucket needs
  no selection and no coordinates.
- **The document does not start at the canvas host's x=0.** The host is
  1078x811 at (92,64) but the document's left edge sits at host x≈137, with the
  app background (grey, luminance ~30) to its left. Derive the edge from the
  frame (first mostly-dark column) instead of assuming it — `diag-canvas-bounds.mjs`
  prints it, and `diag-transparent.png` shows the letterbox clearly.
- **Diff two frames to prove a subtle effect.** Clamp vs Mirror = **0** differing
  pixels; Clamp vs Wrap and Clamp vs Transparent = 33639 px each, confined to an
  85px band starting exactly at the document edge (x=137). Far more convincing
  than a 0.56 change in a global mean.
- **Vite queues a full-reload after source edits, and it lands mid-run.** The
  symptom is `Execution context was destroyed, most likely because of a
  navigation` partway through a probe — not at the start, which makes it look
  random. Log `framenavigated` (it revealed two queued reloads), and absorb them
  by waiting ~2.5s then doing an explicit `page.reload()` before the real work.
- **Poll for a dialog, but keep a settle after it appears.** Swapping a fixed
  `sleep(700)` in `fx-audit.mjs`'s `openLeaf` for a poll that returned the
  instant `.m-dialog` existed made the caller close each dialog mid-mount — and
  then *every* later entry reported "no dialog appeared", which looked like a
  product bug but was pure probe cadence. Poll for presence, then sleep ~600ms
  before the caller reads or closes it.

## Smoke test of all 50 effects -> found a real sign bug in Highlights

Wrote `fx-smoke-all.mjs`: for every menu entry, open it, perturb a parameter,
Apply, and check the canvas actually changed. Two lessons shaped the probe:

- **Many effects are no-ops at their defaults**, so Apply is *disabled* and
  clicking it does nothing — then the following `Ctrl+Z` undoes the *scene
  painting* instead, progressively eating the document. The probe must perturb a
  parameter first and must sleep ~600ms before clicking, or Svelte has not yet
  re-evaluated the derived `noop` and Apply is still disabled.
- **A global mean is the wrong instrument** (a blur conserves it). Diff frames.

Result: 38/50 changed on a black+white scene; the "unchanged" ones were mostly
scene-dependent (Sepia/Hue/Glow are no-ops on black/white, Sharpen is a no-op on
already-maximal edges) and 12 of 14 suspects changed on a colourful Julia base.

The genuine anomaly was **Highlights / Shadows**: `Highlights +90` gave diff 0
while `Shadows +90` gave 763151. First hypothesis was scene-dependence — the
shader masks by luminance (`highMask = pow(luma,3)`, `shadowMask = pow(1-luma,3)`)
and the Julia base was dark (mean ~60), so Highlights was legitimately near-zero.
Retesting on a **bright** base (Clouds, mean 160) *did* make Highlights move — and
revealed the real bug:

```
Highlights +90   mean 160.0 -> 176.7
Highlights -90   mean 160.0 -> 190.4   <-- brighter than +90!
```

### BUG FOUND + FIXED: negative Highlights brightened instead of darkening

`adjustments/highlightsShadows.ts` had a sign asymmetry between two lines that
are supposed to be mirror images:

```glsl
rgb += shadowMask * s * (s > 0.0 ? (1.0 - rgb) :  rgb);   // correct
rgb += highMask   * h * (h > 0.0 ? (1.0 - rgb) : -rgb);   // WRONG
```

With `h < 0` the `-rgb` branch makes it `rgb * (1 + highMask*|h|)` — it pushes
toward **white**, and overshoots, so `-90` came out brighter than `+90`. The
line's own comment above it ("u* > 0 lifts toward white, u* < 0 pushes toward
black") contradicted the code.

Fixed by extracting the shared rule so the two can never drift apart again:

```glsl
vec3 pushLuminance(vec3 rgb, float mask, float amount)
{
	return rgb + mask * amount * (amount > 0.0 ? (1.0 - rgb) : rgb);
}
...
rgb = pushLuminance(rgb, shadowMask, uShadows);
rgb = pushLuminance(rgb, highMask, uHighlights);
```

Verified: `+90 -> 176.7` (up), `-90 -> 114.8` (down), and `+90` now out-brightens
`-90`. New probe `fx-hlsh-assert.mjs` asserts the **direction** of each slider on
a bright base — 5/5 PASS.

Swept the rest of the effects for the same pattern (`? (1.0 - x) : -x`); the only
other hits were a legitimate screen blend (`photo/glow.ts`) and a radial falloff
(`distort/bulge.ts`), both correct.

### Posterize: unreachable `isNoop` (off-by-one in `max`)

`adjustments/posterize.ts` had `max: 255` but `isNoop: levels >= 256`, so the
guard could never fire and Apply was never disabled at the top of the range. The
*threshold* is the mathematically right one — `round(v*(n-1))/(n-1)` is an exact
8-bit identity only when `n-1 = 255`, i.e. `n = 256`; at 255 it rounds into 254
buckets and shifts some channels by one LSB. So the bug was the range, not the
guard: raised `max` to **256**, which makes the guard live and the top of the
slider a true no-op.

### Gotchas worth remembering

- **`EffectDialog` persists last-used settings, so a probe that sets only the
  slider under test is contaminated by the previous case.** My first
  `fx-hlsh-assert` run reported `Shadows +90` as *darker* (160 -> 117.4) purely
  because Highlights was still `+90` from the case before — the dialog reopened
  with it. Reading the sliders back on open made it obvious
  (`opened at [-90, 0] -> set [0, 90]`). Always pin **every** slider in the
  dialog, not just the one under test, and delete
  `paint.svelte.settings.v1 -> effects.<id>` for "default" assertions.
- **A dark test image makes highlight-side effects look broken.** Highlights
  masks by `pow(luma, 3)`, so on a mean-60 base it is a genuine near-no-op. Pick
  the base to suit the effect: bright for highlights, dark for shadows.
- The backtick guard caught me **again** while writing this very fix — my new
  shader comment quoted `` `rgb * (1 + ...)` `` and `scan-shader-backticks.mjs`
  flagged it before it could break the build. Keep shader comments tick-free.
