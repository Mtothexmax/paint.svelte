-- DONE (follow-up: real OS-clipboard paste did not work at all) --
Reported: "it does not really work to paste an image from paint.net to the
browser to paint.svelte". Two root causes, both fixed:

1. Chrome emits a 'paste' event for IMAGE clipboard content ONLY when an
   EDITABLE element has focus. With <body> or a plain <div> focused, Ctrl+V
   with an image on the OS clipboard fires NOTHING (proved in a headed
   Chrome probe: text on the clipboard → event fires; image → no event;
   image + contenteditable/textarea focused → event fires with
   `types: ["Files"]`, `items: ["file/image/png"]`).
   → Added src/lib/components/canvas/pasteCatcher.ts: an offscreen
     <textarea> (tabindex -1, aria-hidden, inputmode none) that owns focus
     whenever no real input does. Ctrl/⌘+V (and Shift+Insert) focuses it
     synchronously from the keydown handler, so the browser's paste command
     has an editable target.

2. Ctrl+V was hijacked by the INTERNAL clipboard:
   keyboard.ts had `v: () => (hasClipboardImage() ? (pasteAsNewLayer(), true)
   : false)`. Once anything had been copied in-app the internal clipboard is
   never cleared, so Ctrl+V forever pasted that stale copy and preventDefault
   killed the native paste — a Paint.NET image never stood a chance.
   → Ctrl+V now only falls back to the internal clipboard when our last copy
     could NOT be mirrored to the system clipboard
     (`systemClipboardHasImage()` in clipboardService.ts). Otherwise the OS
     clipboard always wins.

Also: `isTextTarget()` returns false for the catcher, so it never counts as
"the user is typing" and no shortcut is swallowed; the catcher is wiped on
every `input` / `paste` so stray keystrokes never accumulate.

- Verified in HEADED Chrome with a REAL OS clipboard image + REAL Ctrl+V
  (not synthetic events):
    T1 300x200 image, no in-app copy → +1 layer, no dialog
    T2 in-app Ctrl+A/Ctrl+C first (internal clipboard NON-empty), then a real
       1600x900 OS image → dialog appears (OS image wins), Expand → 1600x900
    T3 2000x1200 OS image → Keep Canvas Size → canvas unchanged, +1 layer
    T4 2400x1400 OS image → Cancel → nothing changes
  Focus regression: text-tool draft still receives typing ("Hello"), dialog
  number inputs still receive typing ("1234"), catcher stays empty, zero
  console errors. tsc + svelte-check clean.

-- DONE (Rotate gizmo: rings fixed + visible before the first click) --
Reported: "for the rotation tool like in blender the circles for each axis must
not move while rotating but stay constant. also they must appear as soon as one
activates the rotate mode and not only when one clicks once."

Two independent causes:

1) THE RINGS SPUN WITH THE CONTENT.
   `MoveEngine.rotateRings` built them as
   `ringPolyline(axis, radius, this.rot3, center)` -- passing the live 3x3
   object rotation into the ring frame, so the gizmo rotated with the thing it
   was rotating. `gizmoRadius()` was also derived from `currentQuad()` (the
   PROJECTED quad), so the rings visibly resized as the content tipped through
   X/Y, and the drag sensitivity (arc length / radius) drifted with them.

   Fixed by giving the rings their own rotation-free frame:
     - new `rotateRingsFor(center, radius)` in render/move/gizmo3d.ts -- always
       IDENTITY3, so only the fixed GIZMO_TILT applies. Blender's gizmo does not
       spin with the object; `rot3` rotates the CONTENT only.
     - new `gizmoRadiusFor(bounds, scaleX, scaleY)` -- from the UNrotated
       selection box, so the radius is constant for the whole gesture.
     - `beginRing()` now hit-tests the exact same `rotateRingsFor(...)` output
       the overlay draws, so a click always lands on what the user sees.
   `AXES3` / `ringPolyline` imports dropped from MoveEngine (now unused there).

2) THE RINGS ONLY APPEARED AFTER THE FIRST CLICK.
   The engine is created lazily and reports `rotateRings: []` until `begin()`
   has lifted the pixels, so the overlay had nothing to draw and rotate mode
   looked like it had no handles at all. Added `activeRotateRings()` in
   EditorCanvas: engine rings if present, else built from `handleBounds` --
   the same fallback `distortQuadPoints()` already used for the distort
   corners. Both `rotateRingPaths` and `ringHandleAt` go through it.

- Verified in headless Chrome (800x600 doc, 300x230 rect selection):
    rings right after picking Rotate, BEFORE any canvas click : x, y, z
    after dragging the Z (blue) ring 90px                     : d identical
    after dragging the X (red) ring 80px (foreshortening)     : d identical
    ring bboxes before / after both drags:
      x:459,205,176,357  y:377,294,364,150  z:411,221,318,338   (unchanged)
    transform log: engine.rotateRingTo 32, engine.transformTo 0, engine.begin 1
      -> both drags hit the rings (no translate fallback), content really turned
  tsc clean, svelte-check 0 errors / 56 warnings (baseline), zero console errors.

  Probe gotcha worth keeping: the ring <path> `d` values are SVG-LOCAL coords.
  The overlay is `absolute inset-0` inside the canvas host, so a probe must add
  `ownerSVGElement.getBoundingClientRect()` before feeding them to
  `page.mouse.move()` -- otherwise the drags land beside the rings and silently
  become translations.
